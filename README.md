# forecast-adaptation

How autoregressive forecast models should be updated when the data-generating process
changes — the surrogate version of the problem operational weather centres face when an
analysis cycle, an observing system, or the forcing itself shifts under a trained model.

Testbed is Lorenz 96, chosen because its error-doubling time (≈2.1 days at F=8) matches the
atmosphere to within a factor of ~1.4 and because forcing is a single controllable knob.
See `docs/TRANSFER.md` for what does and does not carry over, measured rather than asserted.

**Status: substrate imported, experiment design being rebuilt.** No experiment code here yet
— that is deliberate. See "How this repo came to exist" below.

## Data policy

Results are regenerated, not versioned. `.gitignore` excludes `results/`, `figures/`,
checkpoints and all `*.csv` / `*.pt`; `.githooks/pre-commit` rejects any staged file over
1 MB. Committing a curated artifact is still possible and should be a deliberate act
(`git add -f`), not a default.

## How this repo came to exist

Predecessor: `weight-init-effects` @ `7316834`. That repo asked whether warm-starting costs
forecast skill relative to retraining from scratch, at fixed forcing. An audit
(`docs/AUDIT_round1.md`) found the design could not answer it: the do-nothing baseline
(`frozen`, trained once on 2,000 samples) tied the expensive baseline (`cold`, retrained on
40,000 samples every cycle) to within +0.002 MTU across 50 matched pairs. With no separation
between doing nothing and doing the expensive thing, no contrast between them is
interpretable.

The question moved with it. ECMWF hit this for real on 12 May 2026 adapting AIFS to IFS
Cycle 50r1: fine-tuning on new-analysis data alone "either overfitted or failed to
adequately learn the dynamics of the new analysis, depending on the learning rate," while
mixing new with old data worked. What they left open is *how much* new-regime data is
needed, and they report residual regional degradation (~30% in Arctic 2 m temperature) where
the model "has not fully learnt the new near-surface temperature profile." That — the mixing
ratio, and regionally incomplete adaptation — is what this repo is for.

A fresh repo rather than a rewritten history because the predecessor accumulated 262 MB of
permanent git objects from committed result CSVs, and because round 1's design is not
something to carry forward.

## Inherited decisions not yet re-examined

`lorenz96/` was copied verbatim from `7316834`. The numerics are verified — λ₁ matches the
literature at F=8, the tangent linear model tracks divergence across eight orders of
magnitude, attractor statistics match to a total-variation distance of 0.0086 — but the
module encodes methodological choices that were never made explicit. These are open, and
each needs a decision recorded before it is built on:

1. `metrics.nrmse_curve` divides by the standard deviation of the *evaluation window*, so it
   re-normalises per regime. This silently undoes the frozen normalisation `data.py` and
   `docs/TRANSFER.md` exist to protect, and will deflate any comparison at F ≠ 8 (~28% at
   F=12). **This one is a bug, not a judgment call.**
2. `stream.py` seeds training chunks `seed * 31 + c`. Safe now; at `N_CYCLES ≥ 32` different
   seeds silently begin sharing training data.
3. `stream.assert_no_leakage` compares exact float64 bytes across trajectories that are
   independent by construction, so it cannot fail. It provides no evidence for the property
   it names.
4. `metrics.evaluate` defaults to `seed=0`. Callers must pass a held-out seed explicitly —
   the predecessor's `train.py` did not, which made every number in its `RESULTS.md`
   in-sample.
5. `metrics.valid_prediction_time` censors silently at both ends: 0 if the error curve starts
   above threshold, `len(curve)` if it never crosses.
6. `data.load_subset` hard-codes `seed=0` for the underlying pool, so only subset selection
   varies with seed — not the trajectory, not the noise draw.
7. Valid prediction time is quantised to `STRIDE × DT` = 0.05 MTU; differences below ~0.1 MTU
   are at the metric's resolution.
8. `metrics.LAMBDA1` is a hard-coded table measured by `explore.py`, linearly interpolated
   between the measured forcings.

Beyond these, the module fixes `STRIDE=5`, `SPINUP=5000`, `REFERENCE_F=8`, tendency targets
rather than next-state targets, observation noise applied once to the whole trajectory (so
errors are time-correlated), an error threshold of 0.3, and `START_GAP=20` between rollout
initial conditions. None of those are wrong. None were chosen on the record.
